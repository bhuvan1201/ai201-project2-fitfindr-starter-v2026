# Capstone criteria — testability review

This is an AI-assisted testability review of the five user-reviewed capstone criteria. The initial transfer preserved their wording and reasons. Criteria 3 and 4 now have explicit measurement and scoring rules added beneath their retained original sentences. No numerical targets were changed, and formal three-trial evaluation has not run. The earlier Milestone 3 operational measurements remain separate evidence.

| Criterion | How it can be checked | What would make it fail or prevent a verdict |
|---|---|---|
| 1. Hosted workflow completion | Send the stated track-jacket query to the public `/ask` endpoint five times. Save each status and full response. Count a pass only when status is 200 and the selected item, outfit suggestion and fit card are present and non-empty. | Fewer than four complete responses. This measures completion, not factual accuracy or outfit quality. |
| 2. Recoverable structured logs | Send five `/health` requests, retain their `X-Request-ID` values, and recover the corresponding application records from the Vercel runtime logs. Check that each record has timestamp, input, output, status and elapsed-time fields. A GET request can legitimately have null input. | Any request lacks a recoverable record or a required field. A `saved` header alone is not proof that a reviewer can recover the record. |
| 3. Warm hosted response time | Use the track-jacket JSON body for one warm-up attempt, then five sequential uncached measured requests. Wait 10 seconds between attempts, outside the timers. Measure from sending until the full body is received. Keep a failed warm-up separately without replacing it. | Fewer than four measured requests return HTTP 200 with both non-empty outputs in at most 45 seconds. Measured errors, timeouts, incomplete outputs and later instance-initialization delays remain in the score. |
| 4. Reported model usage | Use exactly five uncached track-jacket requests, without replacements; the measured batch from criterion 3 may be reused. Require a completed HTTP 200 response and a matching log with disabled cache, at least two model attempts and positive reported total tokens for every request. | Any failed or incomplete request, unrecoverable record, enabled cache or insufficient usage counter makes that sample fail. A trial with fewer than five passes is MISSED. Distinguish generation failures from logging failures in the diagnosis. |
| 5. Visible logging failure | In an isolated instance of the same application revision, configure a path that actually causes an append failure. Send ten `/health` requests and capture statuses, headers and stderr. Check all three expected observations for every request. | Any request stops returning 200, omits `X-Run-Log: failed`, or lacks a corresponding stderr logging error. A path that can still be created does not trigger the required fault. |

## Fixed measurement setup before formal trials

- **Three trials:** Repeat each complete five-request or ten-request test three times. A trial is the whole group of requests, not one HTTP request. A target must hold in all three trials for an overall MET verdict.
- **Criterion 3:** The query is `90s track jacket in size M`. Each trial has one uncached warm-up attempt and exactly five measured requests, with 10-second pauses outside the timers. A failed warm-up is saved and not replaced; the five measured requests still run. This is an operational warm-up procedure, not proof that all requests share a Vercel instance. Score client wall time through receipt of the complete body; do not remove API waits, retries or later initialization time.
- **Criterion 4:** The sample is a fixed batch of exactly five attempts, without replacements. An error, incomplete output, absent record, enabled cache or insufficient usage fails its sample. Every sample must pass for a 5/5 trial. This makes completion an explicit prerequisite for the five usage observations; a miss must be diagnosed at the stage that actually caused it, rather than automatically blamed on token logging. Preserve all failed attempts.
- **Criterion 5:** A separate local instance permits controlled fault injection without disrupting the public deployment. State explicitly where this test ran. A local application test supports the logging-handler claim, but does not demonstrate recovery from an actual Vercel storage outage. Use a path with a regular file as its parent to force an append failure, rather than assuming a nonexistent directory is invalid. Keep the public service configuration intact.
- **Extension coverage:** All five concern hosted operation or instrumentation; criterion 5 covers the bad path. Their thresholds are unchanged. Their ultimate difficulty is a separate question from whether they can be measured.

The criteria should be committed before formal evaluation results. Earlier deployment smoke evidence is already in Git and must remain identified as such; do not rewrite that chronology.
