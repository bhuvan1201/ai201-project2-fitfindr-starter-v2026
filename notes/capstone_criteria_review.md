# Capstone criteria — testability review

This is an AI-assisted review of the five user-reviewed capstone criteria and reasons transferred from the README. The drafts include AI-provided examples and reasons; this review does not establish unaided authorship. No criterion wording, target or reason was changed during the transfer. No formal trials were run as part of this review.

| Criterion | How it can be checked | What would make it fail or prevent a verdict |
|---|---|---|
| 1. Hosted workflow completion | Send the stated track-jacket query to the public `/ask` endpoint five times. Save each status and full response. Count a pass only when status is 200 and the selected item, outfit suggestion and fit card are present and non-empty. | Fewer than four complete responses. This measures completion, not factual accuracy or outfit quality. |
| 2. Recoverable structured logs | Send five `/health` requests, retain their `X-Request-ID` values, and recover the corresponding application records from the Vercel runtime logs. Check that each record has timestamp, input, output, status and elapsed-time fields. A GET request can legitimately have null input. | Any request lacks a recoverable record or a required field. A `saved` header alone is not proof that a reviewer can recover the record. |
| 3. Warm hosted response time | Record the exact matching query and the warm-up procedure before the trial. Exclude the warm-up request. Time five sequential `/ask` requests from just before sending until the full response body has arrived; inspect the returned suggestion and fit card. | Fewer than four completed responses within 45 seconds. Timeouts and incomplete responses do not qualify. Using different queries or different timing boundaries without recording them would make the comparison inconsistent. |
| 4. Reported model usage | For five actual successful uncached requests, correlate each response with its log and check `model_usage.model_attempts >= 2` and `model_usage.reported_total_tokens > 0`. Retain all failed attempts too. | Any of the five successful requests lacks a record or falls below either threshold. With fewer than five successful requests, the required evidence is incomplete; do not report 5/5. This checks presence of usage, not token-accounting accuracy or billing. |
| 5. Visible logging failure | In an isolated instance of the same application revision, configure a path that actually causes an append failure. Send ten `/health` requests and capture statuses, headers and stderr. Check all three expected observations for every request. | Any request stops returning 200, omits `X-Run-Log: failed`, or lacks a corresponding stderr logging error. A path that can still be created does not trigger the required fault. |

## Measurement setup to settle before formal trials

- **Three trials:** Repeat each complete five-request or ten-request test three times. A trial is the whole group of requests, not one HTTP request. A target must hold in all three trials for an overall MET verdict.
- **Criterion 3:** The sentence does not specify the matching query or the kind of warm-up. A reproducible procedure is to use the track-jacket query from criterion 1, complete one `/ask` warm-up, and then send the five timed requests sequentially. Record the chosen procedure before running it. Use a monotonic clock for durations and preserve client errors and timeouts.
- **Criterion 4:** The sentence assumes five successful generations. Before testing, specify whether the successful sample comes from a fixed attempt set or additional attempts with a declared stopping limit. Do not silently discard failed calls, retry indefinitely until five successes, or count missing evidence as a pass. If fewer than five successes are available, report the available count and the incomplete assessment. These coverage rules need to be settled before claiming this criterion has a formal verdict.
- **Criterion 5:** A separate local instance permits controlled fault injection without disrupting the public deployment. State explicitly where this test ran. A local application test supports the logging-handler claim, but does not demonstrate recovery from an actual Vercel storage outage. Use a path with a regular file as its parent to force an append failure, rather than assuming a nonexistent directory is invalid. Keep the public service configuration intact.
- **Extension coverage:** All five concern hosted operation or instrumentation; criterion 5 covers the bad path. Their thresholds are unchanged. Their ultimate difficulty is a separate question from whether they can be measured.

The criteria should be committed before formal evaluation results. Earlier deployment smoke evidence is already in Git and must remain identified as such; do not rewrite that chronology.
